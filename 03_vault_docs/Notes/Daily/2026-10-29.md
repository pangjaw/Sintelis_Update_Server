## 🗂️ 1. Pemetaan Foto Aset Tunggal Berbasis JSON (`asset_location_mapping.json`)

### Latar Belakang & Masalah:
* Pengguna mengeluhkan pengalaman saat mengedit foto manual:
  Pada berkas PDF yang memuat banyak baris aset di stasiun yang sama (contohnya **Catu Daya / PDSE / Serat Optik / PTDS / PTLS / JPL / PTPP** di Stasiun Cigombong `CGB`), sistem sebelumnya mengekspor folder foto terpisah untuk setiap baris aset (`GENSET ER`, `UPS ER`, `BATTERE BANK ER`).
* Akibatnya, user mendapati 3 hingga 6 folder terpisah yang harus diedit satu per satu, padahal foto fisiknya adalah foto yang sama.
* User menginginkan:
  > *"Output foto tetap HANYA SATU FOLDER berjudul lokasi dari file, tapi ada mapping berbentuk file JSON (`asset_location_mapping.json`) yang berisi pemetaan foto di dalam folder tersebut ke aset yang berada di baris aset file masing-masing."*

### Solusi Teknis yang Diterapkan:
1. **Engine Ekspor Foto (`export_pdf_foto.py`):**
   * Output foto untuk kategori multi-aset per stasiun tetap disatukan ke dalam satu folder lokasi (misal: `03_photos_export/BTP BD/CATUDAYA/CGB/`).
   * Dibangun thread-safe in-memory cache `ASSET_LOCATION_MAP_CACHE` dengan `threading.Lock()` yang mencatat hubungan baris Funcloc, deskripsi aset, file PDF asal, dan folder foto lokasi target.
   * Di akhir eksekusi (atau saat error terperangkap), cache otomatis di-*flush* ke berkas:
     * `03_photos_export/asset_location_mapping.json`
     * `02_server_update/logs/asset_location_mapping.json`
   * Struktur JSON menyediakan indexing instan: `by_location`, `asset_to_location`, `pdf_to_location`, dan `pdf_to_assets`.
2. **Engine Penggabungan PDF (`merge_pdf_foto.py`):**
   * Modul membaca `asset_location_mapping.json` saat start.
   * `get_identifier_candidates()` mengintegrasikan `asset_to_location` sehingga saat merender tiap baris Funcloc pada PDF, sistem secara otomatis menemukan dan meminjam foto dari folder lokasi yang sama.
   * Ditambahkan fitur duplikasi otomatis baris foto pertama (`photo_paths[identifier] = first_found_photos`) jika baris berikutnya belum memiliki folder terpisah, memastikan seluruh baris aset di PDF terisi rapi tanpa status *missing*.
   * **Proteksi Zero-Regression:** Kategori yang memang sudah memiliki foto unik per aset fisik (`WESEL`, `SINYAL`, `AXC`) **DIISOLASI KETAT** dalam himpunan `MULTI_ROW_CATEGORIES` agar alur per aset fisiknya tidak terganggu.
3. **Penyelarasan Penjadwalan (`scheduler.py`):**
   * Menambahkan resolusi alias lokasi `_alternate_ids` (termasuk penanganan prefiks `RADIO_` dan variasi nama stasiun BTP BD).
   * Pada mode bagi aset, durasi dan jam mulai-selesai dihitung proporsional per baris aset namun tetap merujuk ke `location_identifier` yang sama.

## ⚡ 2. Akselerasi Ekspor Foto & Eliminasi Race Condition I/O

### Masalah:
* Proses ekspor foto pada 30–460 berkas PDF memakan waktu sangat lama saat menulis log baris demi baris ke CSV.
* Ditemukan galat `NameError: name 'log_rows' is not defined` pada beberapa cabang eksepsi berkas Wesel.
* Ekspor sering memproses berkas lama yang tidak relevan di dalam folder `backups/` dan `_temp_merged`.

### Solusi Teknis:
1. **Batch Logging ke CSV:**
   * Di [`export_pdf_foto.py`](file:///d:/Dika/Project/Sintelis_Update_Server/01_scripts_pendukung/web-app/timemark_engine/export_pdf_foto.py), logging beralih dari menulis per gambar (`writer.writerow`) menjadi penampungan list `log_rows.append(...)` di memori dan penulisan blok tunggal (`writer.writerows(log_rows)`) yang dilindungi `CSV_LOCK`.
   * Memperbaiki inisialisasi list `log_rows = []` di seluruh blok fungsi sehingga mengeliminasi `NameError`.
2. **Peningkatan Concurrency Worker:**
   * Meningkatkan alokasi thread pool dari 6 menjadi `min(12, max(4, CPU_COUNT))` untuk ekspor foto paralel.
3. **Penyaringan Direktori Sampah (Directory Exclusion Filter):**
   * Direktori `backups`, `_temp_merged`, `05_pdf_merged`, `03_export_foto`, `04_photos_edited`, `.git`, dan `node_modules` secara ketat dikecualikan dari `list_pdf_files()` dan `merge_pdf_foto.py`.

## 🖱️ 3. Stabilisasi Drag & Drop Kartu Foto Anti-Flicker (`GalleryPanel.jsx`)

### Akar Masalah:
* Saat pengguna menyeret (*drag*) berkas foto dari Windows Explorer ke kartu foto di galeri webview, kartu foto berkedip-kedip cepat (*flickering* parah).
* **Penyebab Teknis:**
  Elemen overlay `isDragOver` (`div` dengan latar amber) terpasang di atas kartu tanpa aturan CSS penonaktifan pointer. Saat kursor mouse bergerak di atasnya, browser mengalihkan target hit-test ke elemen overlay. Hal ini memicu event `dragleave` pada container kartu, overlay dicopot, kursor kembali mengenai container dan memicu `dragenter`/`dragover`. Siklus ini berulang pada frekuensi monitor (60Hz–120Hz).

### Solusi yang Diterapkan:
1. **`pointer-events: none` pada Seluruh Lapisan Drag Overlay:**
   * Ditambahkan properti inline `pointerEvents: 'none'` pada semua elemen overlay di Dual View (foto mentah & foto hasil) serta Single View. Kursor mouse tidak lagi terhalang oleh overlay.
2. **Boundary Protection pada `onDragLeave`:**
   * Menambahkan pengecekan relasi target:
     ```javascript
     if (e.currentTarget.contains(e.relatedTarget)) return;
     ```
     Jika perpindahan kursor masih berada di dalam area batas kartu, state drag tidak di-reset sembarangan.
3. **Deduplikasi State `onDragOver`:**
   * Mencegah pemanggilan re-render berulang dengan guard `if (dragOverRel !== targetKey) setDragOverRel(targetKey);`.

## 🎯 4. Preservasi Posisi Kotak Timemark (*Sticky Timemark Coordinates*)

### Akar Masalah:
* Setiap kali foto diganti melalui drag-and-drop, atau saat pengguna membuka kartu foto yang belum memiliki metadata manual, kotak biru penanda timemark (`#38bdf8`) selalu kembali berada di posisi tengah/default `(14, 220)`. Posisi koordinat yang sudah diatur dengan rapi oleh pengguna pada foto sebelumnya tidak diwariskan.
* Backend endpoint `_handle_timemark_replace_photo` sebelumnya menjalankan `edit_timemark_ide1.py --detector guide` tanpa meneruskan flag `--x-override` dan `--y-override`, sehingga foto mentah tanpa garis panduan merah otomatis jatuh ke *stage fallback* tanpa watermark di posisi yang diinginkan.

### Solusi yang Diterapkan:
1. **State Global & Persistensi Browser (`GalleryPanel.jsx`):**
   * Membuat state `lastTimemarkPos` yang membaca dan menulis ke `localStorage.getItem('sintelis_last_timemark_pos')`.
   * Mengintegrasikan callback `onPosChange(newPos)` pada komponen `InlineTimemarkBox` dan `TimemarkEditorModal`. Begitu pengguna menggeser box timemark pada foto mana pun, koordinat terakhir langsung disimpan ke memori sesi dan lokal.
   * `handleDirectDrop` menyertakan `xPos: lastTimemarkPos?.x` dan `yPos: lastTimemarkPos?.y` pada payload POST ke endpoint `/api/timemark/replace-photo`.
2. **Penyempurnaan Backend Handler ([`run_desktop_webview.py`](file:///d:/Dika/Project/Sintelis_Update_Server/01_scripts_pendukung/web-app/run_desktop_webview.py)):**
   * Endpoint `_handle_timemark_replace_photo`:
     * Mengekstrak `xPos` dan `yPos` dari request payload.
     * Jika tidak disertakan, mencari nilai dari `meta.json` yang sudah ada pada folder output aset terkait.
     * Meneruskan `--x-override {xPos}` dan `--y-override {yPos}` bersama flag `--ignore-manual` ke engine `edit_timemark_ide1.py`.
     * Menyinkronkan file foto hasil ke folder alternatif (folder dengan prefix `Tim_1` maupun tanpa prefix).
     * Memperbarui `meta.json` di seluruh direktori terkait dengan koordinat final, tanggal, dan flag `manualEdit: True`.
